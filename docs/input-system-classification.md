# 入力系の分類

キー配列や入力方式は「どんな打鍵で、どんな文字が出るか」を決めるものだが、その仕組みの複雑さは方式ごとに大きく違う。この文書は、IME、タイピングゲーム、キー入れ替えソフト、そして emiel を同じ物差しで並べるための分類を解説する。

定義の厳密な形は [input-system-model.md](./input-system-model.md) にある。この文書ではそれを例で説明し、記号は必要な分だけ使う。

## 4 つの軸

入力系は次の 4 つの組で表せる。

- 打鍵化（B0〜B3）：キー操作のどこまでを見て「1 打鍵」を決めるか
- 変換表（C0〜C4）：打鍵の列から文字への対応がどれだけ複雑か
- 区切りの方針（σ）：打鍵列の切れ目を誰が決めるか
- 読みの方針（ρ）：同じ打鍵に複数の文字が対応するとき、誰が選ぶか

前の 2 つは表現力の軸で、段階が上がるほど表せる方式が増える。後の 2 つは寛容さの軸で、表現力ではなく「どの打ち方を正解として認めるか」を決める。

## 打鍵化：キー操作から 1 打鍵を作る

段階は、打鍵化がキー操作のどの情報を読むかで決まる。上の段階は下の段階の情報をすべて含む。

- B0：押した順序だけを読む。
  - 例：修飾キーを使わない配列。同梱の月配列 2-263 はこの段階。
- B1：押した瞬間に、ほかに何が押されているかも読む。
  - 例：Shift で大文字や記号を打つ直接入力、Shift で小書きのかなを打つ JIS かな、飛鳥配列。
- B2：キーを離した順序も読む。
  - 例：薙刀式、NICOLA、新下駄配列の同時押しを「押している区間が重なったか」で判定する方式。
  - 単独で押せば文字、押したままなら修飾キーになる二役キー（SandS など）もここに入る。離すまでどちらか決まらないため。
- B3：時刻も読む。
  - 例：NICOLA の規格にある「同時打鍵とみなす時間」の判定、携帯入力のタイムアウトによる確定、時間で同時打鍵を判定する親指シフトのエミュレータ。

B0〜B2 は時刻を見ないので、ゆっくり打っても速く打っても、キー操作の順序が同じなら結果は同じになる。B3 だけが打つ速さで結果が変わる。

emiel は B2 まで扱える。同時押しは押下区間の重なりで判定し、時刻は使わない。

## 変換表：打鍵列から文字へ

打鍵が決まった後、打鍵の列を文字に変える表の複雑さを 5 段階に分ける。各段階は、前の段階の制約を 1 つずつ外したものになっている。

- C0：1 打鍵で 1 文字。
  - どの打鍵も単独で文字になり、組み合わせて読む必要がない。
  - 例：直接入力、薙刀式、NICOLA、新下駄配列、飛鳥配列。同時押しの配列も、同時押し全体を 1 打鍵とみなせばここに入る。
- C1：複数打鍵で 1 文字になるものがあるが、ある文字の打鍵列が別の文字の打鍵列の先頭になることはない（接頭符号）。
  - 打鍵列を先頭から読めば、文字の区切りが迷わず決まる。
  - 例：同梱の AZIK。
- C2：ある文字の打鍵列が、別の文字の打鍵列の先頭になりうる。
  - 区切りを決めるには先を見る必要がある。
  - 例：JIS かなの濁点後置。「ふ」の打鍵の後に濁点の打鍵が続くと「ぶ」になるので、「ふ」の時点ではまだ確定できない。同梱の月配列 2-263 もこの段階。
- C3：確定した後に、打った打鍵の一部を次の文字へ持ち越せる。
  - 例：ローマ字の「っ」。`tt` で「っ」を出し、2 つ目の `t` は次の「た」の 1 打目として持ち越す（`tt/っ/t`）。
- C4：持ち越すものが打鍵でなくてもよく、出力のない変換も許す。
  - 例：携帯電話のトグル入力。`a` を押すたびに未確定の文字が あ → い → う → え → お → あ と変わり、何かのきっかけで確定する。未確定の「い」は打鍵ではなく、内部の状態として持ち越される。
  - mozc のテーブル形式は、持ち越しに任意の文字を書けるので C4 まで表せる。

段階の違いは、正解になる打ち方の集合の形に表れる。

- C0〜C3 では、ある単語の正解の打ち方は、打鍵の列として見れば有限個しかない。どの変換も 1 文字以上を出力するので、打鍵数が単語の長さで抑えられるため。
- C4 では無限個になりうる。上のトグル入力で「う」を打つ打ち方は、`a` を 3 回、8 回、13 回…押す打ち方すべてで、式で書けば `aaa(aaaaa)*` になる。
- どの段階でも、正解の打ち方の集合は正規言語に収まる。チョムスキー階層でいえば Type 3（正規）の内側で、この分類はその内側をさらに細かく分けたものに当たる。

emiel は C3 まで扱える。正解の打ち方を DAG（閉路のないグラフ）として構築しているので、閉路が必要な C4 は扱えない。

## 区切りの方針：切れ目を誰が決めるか

C2 以上の表では、同じ打鍵列を複数の区切り方で読める場合がある。たとえばローマ字で `na` は、`n|a`（ん・あ）とも `na`（な）とも読める。この選び方を区切りの方針という。

- 装置が決める（σ = D）：最長一致で区切る。具体的には次の 2 つの条件を課す。
  - 次の 1 打鍵を足すと、より長い打鍵列の先頭になってしまうところでは切らない。
  - より長い打鍵列の途中で打鍵が終わる形では確定しない。
- 目標文字列が決める（σ = T）：打つべき文字列に合う区切り方なら、どれでもよい。

方針による違いの例は次のとおり。

- 「んあ」を打つ場合
  - σ = D：`na` は不正解（「な」と読まれる）。`nna` や `xna` なら正解。
  - σ = T：`na` も正解。
- 単語の末尾の「ん」
  - σ = D：`n` 1 打では確定しない。`nn` が要る。
- トグル入力で「ああ」を打つ場合
  - σ = D：`aa` は不正解（「い」と読まれる）。区切りのキーが要る。
  - σ = T：`aa` も正解。

IME は σ = D で動く。打つべき文字列を知らないので、装置が自分で区切るしかないため。タイピングゲームは答えを知っているので σ = T も選べるが、σ = D にしておくと、実際の IME で通用する打ち方だけを正解にできる。

C0 と C1 の表では、区切り方が 1 通りしかないので、この方針は結果に影響しない。

## 読みの方針：同じ打鍵の読みを誰が選ぶか

複数の表を合わせて使うと、同じ打鍵列に複数の文字が対応することがある。ローマ字の表と直接入力の表を合わせれば、`a` は「あ」とも「a」とも読める。この選び方を読みの方針という。

- 装置が決める（ρ = D）：表の順序などで 1 つに決める。
- 目標文字列が決める（ρ = T）：打つべき文字列に合う読みを選ぶ。

「あいabc」を打つ場合で比べると、違いがわかる。

- ρ = D（IME をオンにしたまま打つ）：`aiabc` は「あいあbc」のようになる。正しく打つには、途中で英数入力に切り替える操作が要る。
- ρ = T：`aiabc` が正解になる。3 つ目の `a` は、目標文字列に合わせて「a」と読む。

タイピングゲームで IME の切り替えを打たずに「あいabc」を打てるのは、ρ = T を採っているからだと説明できる。

## 2 つの方針の関係

区切りも読みも、装置が決める（D）ほうが厳しく、目標文字列に委ねる（T）ほうが寛容になる。同じ打鍵化と変換表なら、正解になる打ち方の集合は次の包含関係を満たす。

- (σ, ρ) = (D, D) ⊆ (D, T) ⊆ (T, T)
- (D, D) ⊆ (T, D) ⊆ (T, T)

よく使われる組み合わせは次の 3 つ。

- (D, D)：IME やキー入れ替えソフト。目標文字列を持たない装置なので、両方とも自分で決める。
- (D, T)：区切りは IME と同じ規則で決め、表の切り替えだけを目標文字列に任せる。emiel のかな入力の既定はこれ。
- (T, T)：目標文字列に合えば何でも正解とする、最も寛容なタイピングゲーム。

## 代表的な入力系の位置づけ

それぞれの典型的な振る舞いを仮定した位置づけで、個々の製品の実装を確かめたものではない。

- IME のローマ字入力（かな漢字変換の前まで）
  - 打鍵化 B1、変換表 C3（mozc の一般形は C4）、(σ, ρ) = (D, D)
- 携帯電話のトグル入力
  - 打鍵化 B3（タイムアウトで確定する場合）、変換表 C4、(D, D)
- キー入れ替えソフト（Karabiner、AutoHotkey など）
  - 打鍵化 B0〜B1（時間で同時打鍵を判定するものは B3）
  - 変換表 C0〜C1。出力は文字ではなく、別のキーの操作になる
  - (D, D)
- emiel（ローマ字 + 直接入力の既定構成）
  - 打鍵化 B2、変換表 C3、区切りはかなのエントリが D で英数のエントリが T、ρ = T
- 寛容なタイピングゲーム
  - (T, T)。打鍵化と変換表は方式による

## 同梱プリセットの分類

emiel に同梱しているルールの、合成前の表を調べた結果。打鍵化の段階は表の特徴から判定した。修飾キーを使う打鍵があれば B1、同時押しがあれば B2 とした（emiel の打鍵化は、同時押しの判定に離した順序を使うため）。

- ローマ字：B1、C3
  - Shift を使う記号がある。`n` が `nya` などの先頭になり、`tt/っ/t` の持ち越しがある。
- AZIK：B1、C1
  - どの打鍵列も別の打鍵列の先頭にならない。
- JIS かな：B1、C2
  - 濁点・半濁点を後置するため、清音の打鍵が濁音の打鍵の先頭になる。
- 月配列 2-263：B0、C2
- 飛鳥配列（123、290）：B1、C0
- 薙刀式 v15：B2、C0
  - 同時押しに加え、Space を押したまま打つ修飾がある。
- NICOLA、新下駄配列：B2、C0
- 直接入力：B1、C0

JSON 形式で読み込むルールは、区切りの方針の既定が T になる。JIS かなと月配列 2-263 は C2 だが、区切りは目標文字列に委ねている。

## emiel で扱えない領域と、扱う場合に必要なこと

- 時刻を使う打鍵化（B3）
  - 打鍵化の判定に時刻を渡し、閾値で同時打鍵やタイムアウトを判定する仕組みが要る。
- 閉路のある変換表（C4）
  - 正解の打ち方を DAG ではなく、閉路を許すグラフとして構築する必要がある。
  - 未確定の文字（トグル中の「い」など）を画面に出す手段も要る。
- 同時押しの順序の区別
  - emiel の同時押しはキーの集合なので、「A を先に押して B を重ねる」と「B を先に押して A を重ねる」で別の文字を出すことはできない。順序を区別したい場合は、先に押すキーを修飾キーとして書く。

## この分類で扱わないこと

次の性質は、表現力とも寛容さとも別に決まるので、分類には含めない。同じ位置づけの入力系どうしでも、ここが違えば遊び心地は変わる。

- ミスの数え方：正解でない打鍵のうち、どれをミスとして数えるか。
- 判定の待ち時間：打鍵を受けてから、正解かどうかを確定するまでにどれだけ待つか。
- 取り消し：Backspace でどこまで戻せるか、取り消した打鍵を統計でどう扱うか。
